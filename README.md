# claude-kb

A Markdown knowledge base on using Claude efficiently, written for agents to query: model and effort choice,
subagents and orchestration, agents in repos, token usage, caching and research-tool cost, writing skills, hooks,
parallel sessions, agents with cloud and cluster access, prompting the current models, session workflows, memory and
instruction files, the desktop app, artifacts and remote surfaces, and web analytics and SEO work. Every entry carries its sources, a confidence
level and a last-verified date.

## Querying it

From any repo, the `claude-kb-lookup` skill answers questions from this knowledge base and cites entry IDs. It lives in
the `freek-local-skills` plugin of [FreekMencke/claude-skills](https://github.com/FreekMencke/claude-skills)
(`local-skills/skills/claude-kb-lookup/`); install it with that repo's `install.sh`.

- It runs as a forked subagent on Haiku (`context: fork`), so the index stays out of the caller's context: a lookup
  cost about 0.19 USD against 0.57 inline, with the same entries and facts (FreekMencke/claude-skills#7, 2026-10-12).
- The fork can't see the conversation, so pass it a self-contained question, and keep its entry IDs in the reply.
- It reads a local clone at `/home/fremen/repos/claude-kb` and fast-forwards it before each lookup, so it doesn't work
  in cloud sessions.

By hand: start at [INDEX.md](INDEX.md) and find the question in Quick answers, or grep [ENTRIES.md](ENTRIES.md) for the
entry's ID, title or tags (`grep -i -E 'webfetch|curl' ENTRIES.md`), then read only that entry:

```bash
grep -n '^## \[TOK-036\]' topics/kb-*.md
```

Treat an entry last verified more than 60 days ago as a lead to re-check, not a fact.

## Changing it

- Follow the entry format in [CLAUDE.md](CLAUDE.md). When an entry is added or its title or tags change, edit the topic
  file's index row and run `python3 scripts/check_kb.py --write` to regenerate ENTRIES.md.
- Run the check after any change to entries. CI runs it on every push to `main` and every PR.

  ```bash
  python3 scripts/check_kb.py
  ```

## Monthly re-verification

A cloud routine, [claude-kb monthly re-verification](https://claude.ai/code/routines/trig_01HDV9ENf7vGtyTF52Lb4qTW),
runs at 06:00 UTC on the 1st of each month on Sonnet 5.5. It re-checks every official-docs and official-example entry
against its sources, sets Last verified, logs corrections in CHANGELOG.md, checks new and changed entries for
overlap with other files, and opens a PR from `claude/reverify-<YYYY-MM>`. Its prompt lives in the routine, not in this repo.

- **Why a PR, not a push to main:** a wrong correction to an entry every agent trusts should be reviewed first.
- **Why its subagents curl and grep sources for exact wording:** the first run ([FreekMencke/claude-kb#1](https://github.com/FreekMencke/claude-kb/pull/1)) changed 25 entries and 8 of
  those were wrong, 6 of them claims it couldn't find in a truncated fetch and then removed or marked unverified. Now a
  claim it can't find stays and is listed as "not found"; only a contradicting quote changes it.
- **Why it looks for overlap, and only in new and changed entries:** the per-file subagents can't see other files, and
  the topic files were reconciled once in full (FreekMencke/claude-kb#28). The lead resolves each overlap and each
  `check_kb.py` duplicate warning as an Overlaps line, a merge, or a "Similar but distinct" line in OVERLAPS.md, and lists
  them under "Overlaps" in the PR body.
- **Reviewing it:** spot-check the removals and "unverified" marks before merging.
- **Debugging it:** RemoteTrigger `list_runs` and `get_run_log`. Pause or delete it at https://claude.ai/code/routines.
- It opens the PR with the cloud session's GitHub tool, because `gh pr create` uses GraphQL, which returns 403 in
  cloud sessions.

## Design decisions

- **Plain Markdown in git, no memory connector or vector search.** At this size an index plus grep beats semantic
  search, files stay reviewable, and no tool definitions are added to every session. Revisit if lookups start failing
  or the knowledge base sprawls.
- **Opus leads, Sonnet readers.** New research sessions ran with an Opus 5.5 lead at high effort and Sonnet subagents
  (or a workflow) reading sources. The hard part is judging and reconciling sources; Haiku readers risk errors in a
  knowledge base every agent trusts.
- **Only the lead writes files.** Research subagents return findings with source URLs ([CLAUDE.md](CLAUDE.md)).
- **Facts apart from recommendations.** Recommendations are specific to our setup and go stale faster.
- **A file per kind of question, not per feature.** Prompting (how to word an instruction) and memory (where it lives
  and when it loads) are separate files because agents look them up separately; research-tool cost is a section of
  `kb-token-usage.md`, not a file, because it's a handful of entries (FreekMencke/claude-kb#18).
- **Link, don't repeat.** Each topic file opens with what it links to instead of covering; neighbouring entries that
  stay separate are listed in OVERLAPS.md's "Overlaps kept on purpose", and duplicates are merged with a pointer (never
  renumbered).
- **One home per open question.** When two files raise the same question, one keeps it and the other points there.
  Cross-file pointers name entry IDs, not the issue that created a topic.
- **INDEX.md holds only what answers a lookup.** The lookup skill reads it in full on every question, so the curation
  records and the change history live in OVERLAPS.md and CHANGELOG.md; Conflicts stay because they decide an answer.
- **The entry list is grepped, not read.** It grew by about 1.6 KB per 10 entries and was two thirds of INDEX.md (51 of
  74 KB at 504 entries), so it moved to a generated ENTRIES.md that lookups grep. Topic files live in `topics/` so the
  root holds only the entry points and the curation files (2026-10-13).
- **INDEX.md's Quick answers stay near 30 rows** across all topics; each topic file keeps its own 10–15.
